# zendb-types

`zendb-types` owns ZenDB's portable data model and shared binary utilities. It
contains persisted libp2p identity values, but no swarm, storage configuration,
or runtime policy.

## Workspace Values

`InstallationId` is the logical event author and installation-table key.
`WorkspaceId` identifies a replicated workspace. Both are distinct opaque
eight-byte types generated by the ID macro.

`PublicKey` wraps `libp2p_identity::PublicKey` and bincode-encodes libp2p's
canonical protobuf representation. `Multiaddr` wraps the standalone
multiaddress type.

`Installation` contains a display name, workspace-derived public key, route
hints, and `InstallationState`. It is a registered leaf CRDT:

- `Pending`: visible to managers but has no authority;
- `Rejected`: retains the explicit admission decision and has no authority;
- `Active(Permissions)`: participates according to its permissions.

`Active` has higher merge precedence than both `Pending` and `Rejected`, so
concurrent discovery or rejection cannot demote an active installation.
`Pending` and `Rejected` have equal precedence and resolve by event stamp;
concurrent `Active` updates also resolve by event stamp.
Installation removal is represented by `Rejected`, not a Cell tombstone, so
every registry mutation remains inside the same convergent state lattice.

Permissions are `ReadData`, `WriteData`, `ManageTables`, and
`ManageInstallations`. ZenDB does not define roles; applications may compose
their own roles from permissions. Neutral built-in bundles cover read-only,
read-write, table-control, installation-control, and full access.

Applications provide the root identity through:

```rust
pub trait PeerIdentity: Send + Sync {
    fn keypair(&self) -> &libp2p_identity::Keypair;
    fn display_name(&self) -> &str;
    fn addresses(&self) -> Vec<Multiaddr> { Vec::new() }
}
```

`addresses` supplies durable route hints for the local Installation. The
default is empty so identities that do not publish routes need no extra code.

## Replicated Events

Events carry no per-event signature. RBAC is enforced by the producing device
before local insertion. Network batches, receipt summaries, and fetch ranges
remain private to `zendb-workspace`.

## CRDT Data

`EventId` is `(InstallationId, sequence)`. Sequence allocation is scoped by
the physical table that owns the event; replication carries that table context
alongside the ID. `EventStamp` adds hybrid logical time and orders by
`(physical_ms, logical, author, sequence)` within a table.

The value set includes scalars, Installation, Counter, multi-value register,
OR-set, set, priority queue, collaborative text, Record, and List. Record and
List support recursive path traversal.

## Binary Utilities

`utils::serdes` is the shared bincode layer with little-endian fixed-width
integers, serialized sizing, direct buffer writes, and vector serialization.
`Blob::encode` and `Blob::decode` use the same configuration.
